# 项目长期记忆与后续研究约束（2026-04-16）

本文档用于记录 `mem-ace / ace_dinov2_lmc` 当前已经明确的长期方向、设计约束与后续研究重点，作为后续代码修改、实验设计与文档更新时的统一参考。

---

## 1. 当前训练范式只是阶段性结果，长期目标是多场景联合训练

- 当前结果本质上仍然是：**单场景、单 FPS memory、单场景训练**。
- 这只是第一阶段验证，不是最终目标。
- 长期目标是：
  - 进行 **多场景联合训练**；
  - 得到真正更通用的 LMC，而不是只对单场景有效；
  - 若场景尺度继续增大，则需要进一步考虑 **sub-memory** 方案。
- 换句话说，未来的系统不应只服务于「一个场景一个 memory 一个模型」，而应逐步走向：
  - 单模型处理多场景；
  - 大场景下可按子区域组织 memory；
  - 最终具备更强泛化能力与可扩展性。

---

## 2. 特征坐标系与点云坐标系必须严格对齐：统一到参考坐标系

### 2.1 当前问题

- 现有 memory 中，特征提取方式（尤其 MapAnything）是在**参考坐标系**下进行的；
- 但点云当前仍主要保存在**世界坐标系**下；
- 这会在 feature 与 point cloud 之间引入坐标系 gap，导致二者并非严格一一对应。

### 2.2 后续明确要求

后续 memory 构建应改为：

1. 先通过位姿矩阵把点云从**世界坐标系**转换到**参考坐标系**；
2. 在参考坐标系下完成 feature 与 point cloud 的严格对齐；
3. 后续推理也应优先在**参考坐标系**下进行；
4. 模型输出的 scene coordinates 在使用或评测前，再从参考坐标系变换回世界坐标系。

### 2.3 scene center 约束

- 虽然坐标系会改到参考系，但 **scene center 仍然采用当前策略**：
  - **所有相机位姿（相机中心）的均值**。
- 这是当前已经验证过效果较好的做法，不能轻易改掉。
- 也就是说：
  - 坐标系统一到参考系；
  - 但 scene center 的定义仍沿用「相机位姿均值」。

### 2.4 对大场景 / 子场景切分的启发

- 对于大尺度场景，可以借鉴 **ACE 原版在 Cambridge 数据集上的做法**：
  - 先对数据集进行聚类；
  - 得到多个子数据集；
  - 每个子数据集再分别训练。
- 我们这里虽然**严格要求最终仍尽量由一个模型完成训练**，但这个“先切分再组织”的思路非常值得借鉴。
- 因此后续可考虑：
  - 先把一个大场景切分为若干子数据集 / 子区域；
  - 在子区域下构建 **sub-memory**；
  - 实现更明确的局部隔离与局部一致性。

---

## 3. 若采用 sub-memory，路由与结果融合是核心开放问题

如果未来引入 sub-memory，则必须认真设计以下问题：

1. **如何决定当前 query 应该使用哪一个 sub-memory？**
2. **是先做 routing，再只在被选中的 sub-memory 上推理？**
3. **还是对多个 sub-memory 分别推理，再做结果融合？**
4. **如果进行融合，融合是在 feature 层、scene coordinate 层，还是 pose 层？**
5. **是硬路由（选一个）还是软路由（多个加权）？**

这些问题目前都不能草率决定，需要作为后续 sub-memory 方案中的重点研究对象。

---

## 4. 归一化路线必须被高度重视：这是多场景联合训练的关键

### 4.1 归一化的重要性

- 归一化不是附属选项，而是未来实现 **多场景联合训练** 的关键组成部分。
- 不同场景可能存在显著尺度差异；
- 若不做归一化，大尺度场景会在训练中占据过大的 loss 分量，破坏多场景平衡。
- 当前很多 feed-forward 3D reconstruction 方法（如 VGGT、MapAnything 等）也都使用归一化策略，其原因正是为了缓解尺度差异问题。

### 4.2 我们这里的坐标链路

结合前面的参考坐标系统一，未来应明确意识到这里至少会出现三层变换：

1. **世界坐标系**
2. **参考坐标系**
3. **归一化坐标系**

也就是：

- 世界 → 参考 → 归一化
- 使用时再：归一化 → 参考 → 世界

因此后续实现中必须非常清楚地区分：

- 世界坐标；
- 参考坐标；
- 归一化坐标；
- scene center 与 normalization stats 分别属于哪一层。

### 4.3 原则

- 训练时可在归一化坐标系中进行，以获得更稳的多场景联合训练；
- 最终输出 / 使用时，再还原回目标坐标系；
- 但必须始终保证变换链条清晰可逆。

---

## 5. MapAnything 的多视图推理显存压力需要通过 training-free 方法优化

### 5.1 现状

- MapAnything 在同时推理较多视图时，显存压力很大；
- 这已经成为 memory 构建和大规模多视图推理中的重要瓶颈。

### 5.2 后续方向

后续需要重点关注 **training-free** 的加速与显存优化方法，以减少显存压力并提高推理速度。

当前已明确可参考的方向包括：

- **AVGGT: Rethinking Global Attention for Accelerating VGGT**
- **Faster VGGT with Block-Sparse Global Attention**

此外，也应主动关注：

- MapAnything 本身是否有后续工作或改进分支；
- 其他针对大视图数全局 attention 的稀疏化 / 分块化 / 近似化方法；
- 是否能在不破坏几何一致性的前提下，对 MapAnything 推理阶段做 attention 结构裁剪或局部化。

这部分后续应作为 memory extraction / feature extraction 速度优化的重要方向。

---

## 6. memory 中尚未充分利用的信息（射线、普吕克射线等）要保留为后续结构改进接口

- 当前 memory 中已经保留了许多暂时还没有真正用起来的信息，例如：
  - 射线；
  - 普吕克射线表示；
  - 其他与几何视角相关的派生量。
- 这些内容不能视为冗余垃圾；
- 它们应当被视为后续改进：
  - **LMC 模块设计**；
  - **head 结构设计**；
  - feature-memory 对齐方式；
  - query-memory 几何约束；
  的重要接口。

也就是说：

- 现在可以暂时不用完；
- 但必须有意识地保留；
- 后续结构设计时，应优先考虑如何把这些几何信息重新引入模型，而不是把它们删掉。

---

## 7. 目前建议的统一理解

当前项目可以按下面的长期路线理解：

1. **短期**：单场景 memory + 单场景训练，验证 LMC 管线有效；
2. **中期**：统一参考坐标系，强化归一化路线，引入更合理的大场景 / 子场景组织；
3. **中长期**：多场景联合训练，形成真正通用的 LMC；
4. **进一步**：在大尺度场景中采用 sub-memory，并认真研究路由 / 融合机制；
5. **结构升级**：重新利用 memory 中保留的射线、普吕克射线等几何信息，优化 LMC 与 head 的具体设计。
