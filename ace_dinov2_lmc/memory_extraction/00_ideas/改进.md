1. Problem Restatement
当前要设计的不是一个单点优化，而是一套完整的 memory construction policy。目标是在同一系统内同时支持两类场景：
1. 小场景 / 中等场景优先采用 single-forward memory construction，保证 MapAnything 在单次 multi-view forward 中得到统一的 reference-conditioned feature space，避免额外的跨 chunk 特征/参考系偏移。你当前仓库的 memory extraction 主路径本身就是按这一思路实现的：先做 view selection，再把 memory_views 整体送入一次 MapAnything infer()，并读取共享中间特征 。
2. 大场景 / 多区域弱连通场景当单次 forward 的几何工作域明显不够时，系统需要自动切换到 cluster-based branch。这部分不应重新发明聚类，而应复用 ACE 原版的场景聚类思想：README 已明确说明 --num_clusters / --cluster_idx 是官方 ensemble 路线的一部分 ，而 dataset_origin.py::_cluster() 给出了具体实现——基于相机中心的层次式二分 kMeans，每次拆当前最大簇，直到达到目标簇数 。
因此，整体设计目标不是“把 ASB 再调几个参数”，而是构建一个场景自适应的 memory policy controller，它要统一解决三件事：
* single 分支里，具体怎么选帧
* 什么时候自动停止继续加帧
* 什么时候自动切到大场景 cluster 分支
约束也很明确：
* 小场景里，默认不做多块独立 forward，因为你已经指出这会引入 reference-conditioned feature space 的额外 gap；更合理的 contract 是保持 single forward 和统一参考系 。
* 大场景里，不应执着于单次 forward 全吞，而应允许 cluster route。
* 设计必须兼容你当前代码中的 adaptive ASB 雏形，例如 anchor_support_select_views()、_estimate_adaptive_asb_scene_params()、_prune_candidate_pool_to_budget() 以及现有的 adaptive coverage / early stop 逻辑 。

2. Design Space Exploration
方案 A：固定视图数的单分支 single-forward
核心思想对所有场景固定选择 K 张 memory views，例如 32 或 40，然后一次性做 single-forward memory extraction。
优点
* 实现最简单。
* 实验对比公平，容易复现。
* 工程上和你当前管线最接近。
缺点
* 小场景往往不需要那么多视图，继续加帧可能只会引入弱共视、长桥接、参考距离过远等风险。
* 大场景时固定 K 又可能根本不够，单批覆盖不可能达标。
* 它把“场景规模差异”硬塞进同一个固定预算里，本质上不自适应。
适用场景
* 数据集内部场景规模接近。
* 只想快速做 baseline。
失效方式
* 小场景过选；
* 大场景欠选；
* 对 reference choice 和 scene layout 敏感。

方案 B：全场景统一采用 cluster/chunk 路线
核心思想不区分场景大小，全部先切成多个 cluster，再分别处理。
优点
* 大场景 naturally scalable。
* 单个 cluster 内的几何范围更小，更容易满足局部稳定性。
缺点
* 小场景会被不必要地切碎。
* 你已经明确指出：MapAnything 多视图特征更接近 reference-conditioned latent space，若小场景也切成多个独立 chunk，会引入多个 reference-conditioned feature subspaces，进而产生额外 mismatch 风险 。
* 系统复杂度明显增加。
适用场景
* 明确的大型 outdoor / campus / multi-zone scene。
* 已经接受 ensemble / chunk-level routing。
失效方式
* 小场景被过度工程化；
* reference-space 一致性被破坏；
* 后续 query routing 成为新难点。

方案 C：single-forward + 自适应停帧，但没有大场景切换
核心思想所有场景默认 single-forward，只给一个 max_views 上限；选帧过程中根据 coverage / support / gain saturation 自动停止。
优点
* 很符合小场景诉求。
* 兼容你当前 adaptive ASB 代码结构，因为仓库里已经有 covis_adaptive_asb、covis_adaptive_view_count、coverage target、gain patience 等雏形 。
* 解决了“固定视图数不合理”的问题。
缺点
* 对真正的大场景不够。它只能回答“该不该早停”，不能回答“单个 forward 根本装不下怎么办”。
适用场景
* 绝大多数 indoor / room-scale / compact scene。
* 你当前的主问题域。
失效方式
* 大场景虽然 stop 机制正常，但 single-forward 的几何工作域本身已经失效。

方案 D：双分支自适应策略
small-scene single-forward auto-stop + large-scene auto-cluster
核心思想引入一个上层 scene policy controller：
* 默认走 single-forward 选帧分支；
* 若 scene statistics 表明单批 forward 已明显不适配，则自动切到 cluster branch；
* cluster branch 复用 ACE 原版的层次聚类逻辑。
优点
* 与你的系统约束最一致。
* 小场景保留统一 reference-conditioned feature space。
* 大场景具备可扩展性。
* 和现有代码自然衔接：single 分支继承 ASB，large 分支继承 ACE cluster 思想。
缺点
* 需要设计额外的 policy gate。
* 系统复杂度高于单分支。
* 需要更完整的评测设计。
适用场景
* 你的当前目标最匹配。
结论我建议选择 方案 D。但它不是“两个分支并列摆着”，而是一个明确的层级结构：
1. 第一层：scene policy estimation
2. 第二层：small-scene single-forward TA-ASB
3. 第三层：large-scene ACE-style clustering branch

3. Selected System Architecture
我选择的总体架构是：
Adaptive Memory Policy Architecture
包含三个核心模块：
模块 1：Scene Policy Estimator
职责：
* 读取全场景 camera centers / covisibility / reference distance 等统计；
* 判断当前 scene 是否仍适合 single-forward；
* 若不适合，决定是否进入 cluster branch，以及 cluster 需要拆到什么程度。
模块 2：Single-Forward Topology-Aware ASB
职责：
* 在默认 small-scene 路线下进行单批选帧；
* 不再固定选择 K 张，而是只给 max_views；
* 逐步加入视图，并根据 coverage、topology、support 的联合 adequacy 判据自动停止。
模块 3：ACE-Style Cluster Branch
职责：
* 对 large scene 进行层次化 camera-center clustering；
* 在每个 cluster 内部再运行 local single-forward selector；
* 输出 cluster-specific memories 与 cluster metadata，供下游 query routing / ensemble evaluation 使用。
为什么选这个架构
因为它满足三个全局一致性要求：
1. 小场景优先保证统一特征参考系不轻易引入 chunk-level reference gap 。
2. single 分支内部的核心优化对象正确不再只是 coverage，而是“适合单次 forward 的 selected view graph”。
3. 大场景时具备自然退化路径不是硬顶 single-forward，而是自动切到 ACE 已验证过的 cluster 路线 。

4. Detailed Pipeline Design
下面给出完整的 step-by-step 设计。
Stage 1
Scene Graph Precomputation
输入
* 全部训练视图的 camera poses / centers
* covisibility matrix 或你当前代码里已有的 covis_strength
* reference candidate 信息
输出
* scene-level statistics
* global view graph
* reference-related statistics
* policy decision 所需的 probe 指标
算法
1. 计算所有 camera centers。
2. 构建全局视图图 (G=(V,E))：
    * 节点：views
    * 边权：covis_strength[i,j]
3. 计算 scene statistics：
    * scene extent / bbox diagonal
    * reference distance quantiles（例如 q80 / q90 / q95）
    * strong-covisibility graph 的 component 数量
    * giant component ratio
    * supportable ratio
4. 运行一个轻量 probe：
    * 在 max_views 上限下模拟一次 reference-safe FPS 或当前 ASB 初筛
    * 记录 probe coverage 与 probe topology
表示
* scene_stats
* global_graph_stats
* probe_stats
这一步本质上把“场景是否适合 single-forward”从直觉变成显式统计问题。

Stage 2
Scene Policy Estimation
输入
* scene_stats
* global_graph_stats
* probe_stats
输出
* policy = single_forward | cluster_branch
* 若为 cluster branch，则输出 cluster_plan
算法定义一个 rule-based large-scene gate，先不建议一开始就学习它：
触发 large-scene branch 的典型条件可以是：
* 几何尺度过大：extent_diag > τ_extent
* 单 reference 风险高：ref_q90 > τ_ref
* supportable ratio 太低：supportable_ratio < τ_support
* global graph 天然碎裂：num_components > 1 且 giant_component_ratio < τ_gc
* 在 max_views probe 下仍明显无法满足 coverage target：probe_coverage_max > c * target_coverage_max
若未触发，则进入 single-forward 分支。若触发，则进入 cluster 分支。
表示
* policy_decision
* large_scene_reason_codes
这样后续日志里可以明确知道：某个 scene 为什么被判成 large scene，而不是一个黑盒 if。

Stage 3
Small-Scene Branch: Candidate Pool Construction
输入
* 全部 views
* root/reference
* covis_strength
* adaptive scene parameters
输出
* candidate pool
* initial selected seed set
算法这一部分继承你当前 anchor_support_select_views() 的主干，而不是推翻：
1. 选择 root/reference。
2. 调用 _estimate_adaptive_asb_scene_params() 或其升级版，估计：
    * safe_dist_to_ref
    * ref_dist_max_limit
    * target_coverage_mean/max
    * support_tau
    * min_coverage_gain等参数
3. 筛掉明显不 supportable / 明显过远 / 明显低质量的候选。
4. 得到一个safe-but-not-too-small 的 oversampled candidate pool。
表示
* candidate_ids
* candidate_features
* candidate_graph
这里的关键是：candidate pool 不是最终解，只是后续 topology-aware incremental selection 的搜索空间。

Stage 4
Small-Scene Branch: Topology-Aware Incremental Selection
输入
* candidate pool
* max_views
* min_views
* coverage targets
* selected graph 当前状态
输出
* final selected set (S)
算法采用 TA-ASB：Topology-Aware ASB。在当前 ASB 基础上，把 greedy 评分从“coverage + pairwise conn”升级成“coverage + support + topology”。
4.1 维护 selected induced graph
对当前 selected set (S)，定义诱导子图 (G_S)：
* 节点：selected views
* 边：covis_strength >= tau_graph
4.2 每次加入 candidate 时计算四类收益
A. Coverage gain
* 沿用当前 _coverage_gain_scores() 的思想
B. Support gain
* 与 selected 的 max covis
* 与 selected 的 shared-neighbor count
* 局部 degree 提升
C. Topology gain
* 是否减少 component 数
* 是否提升 minimum degree
* 是否减小 disconnected / isolated 风险
* 是否降低 articulation / bridge risk
* 可选：是否提升 (\lambda_2)（谱连通性）
D. Reference risk
* 是否明显推高 ref distance mean / max
* 是否消耗 far-view budget
4.3 Greedy score
采用加性更稳定：
[Score(v \mid S)=w_c \Delta Cov(v)+w_s \Delta Supp(v,S)+w_t \Delta Topo(v,S)
w_r Risk_{ref}(v)]
我不建议继续主要用乘性形式，因为在引入 topology 后，加性更可控，也更便于调试和解释。
4.4 初始 seed
建议不是只用 root，而是：
* root
* 1–2 个与 root 高 support 的 anchor
* 1 个 coverage 扩展点这样能更快构造出一个健康初始图，而不是从单点开始长链式生长。
表示
* selected_ids
* selected_graph_stats
* selection_trace

Stage 5
Small-Scene Branch: Adaptive Stop Controller
输入
* 当前 selected set (S)
* coverage / topology / support 统计
* recent gain history
* max_views
输出
* stop / continue 决策
算法这是整个系统的核心之一。不再要求手工给定固定 n_memory，而是只给 max_views，其余交给 adequacy controller。
定义三类 stop 条件：
Stop Condition A：Coverage adequacy
例如：
* coverage_mean <= target_coverage_mean
* coverage_max <= target_coverage_max
Stop Condition B：Topology adequacy
例如：
* num_components == 1
* isolated_count == 0
* degree_min >= 2
* articulation_count <= τ_art
* diameter <= τ_diam
Stop Condition C：Marginal utility saturation
维护最近 (p) 次新增 view 的改进：
* Δcoverage_mean
* Δcoverage_max
* Δnum_components
* Δdegree_min
* Δlambda2（可选）
若最近 (p) 步改进都低于阈值，且已达到 min_views，则 early stop。
Unified adequacy score
为了实现更平滑，可以定义：
[Q(S)=1
* a \cdot \frac{cov_mean}{\tau_{mean}}
* b \cdot \frac{cov_max}{\tau_{max}}
* c \cdot component_penalty
* d \cdot bridge_penalty
* e \cdot isolated_penalty]
当：
* Q(S) >= τ_Q
* 最近 ΔQ 小于阈值
* |S| >= min_views
则停止。
表示
* stop_reason
* final_view_count
* adequacy_trace
这一步使得单场景不再依赖固定视图数，而是变成任务驱动的自适应停止。

Stage 6
Small-Scene Branch: Topology-Constrained Repair
输入
* 初步 selected set
* remaining candidate set
输出
* repaired selected set
算法保留你当前 _prune_candidate_pool_to_budget() 里的 repair 思路，但修改规则：
1. 先做 connectivity repair；
2. 再做 coverage-hole repair；
3. 所有 repair candidate 必须先通过 topology gate：
    * 不允许引入新的 component fragility
    * 不允许显著推高 articulation / bridge risk
也就是说，repair 不再是单纯修 coverage tail，而是在 topology safety margin 内修 coverage。

Stage 7
Large-Scene Branch: ACE-Style Hierarchical Clustering
输入
* 全部 camera centers
* policy = cluster_branch
输出
* clusters
* cluster metadata
算法直接复用 ACE 原版 dataset_origin.py::_cluster() 的思想 ：
1. 初始时所有 views 在一个 cluster。
2. 每次挑当前最大 cluster。
3. 在该 cluster 的 camera centers 上做 k=2 kMeans。
4. 更新 cluster list。
5. 直到达到目标 cluster 数。
但这里不应强制预设固定 num_clusters。建议改成 split-until-safe：
* 不是“拆到 4 个就停”
* 而是“只要某 cluster 还不满足 single-forward-safe 条件，就继续拆”
cluster safe 条件
对每个 cluster 单独检查：
* local extent 是否小于阈值
* local graph 是否基本连通
* local max_views_per_cluster 下 coverage 是否可达标
* local reference distance quantiles 是否在安全范围内
这样 cluster 数由 scene 决定，而不是手工固定。
表示
* cluster_assignments
* cluster_centers
* cluster_safe_flags

Stage 8
Cluster-Local Memory Construction
输入
* 每个 cluster 的 local views
输出
* cluster-specific memories
算法每个 cluster 内，复用 Stage 3–6 的 small-scene single-forward TA-ASB。
也就是说：
* cluster branch 不是另写一套 memory selector；
* 而是每个 cluster 内部仍然运行 single-forward selector。
这样整个系统保持模块复用和逻辑一致性。

Stage 9
Memory Packaging and Downstream Interface
输入
* single scene 或多个 clusters 的 selected views
* extracted features
* geometry / metadata
输出
* final memory package
表示对于 small-scene：
* mode = single_forward
* selected_views
* selection_trace
* policy_stats
对于 large-scene：
* mode = clustered
* clusters[]
    * cluster_id
    * selected_views
    * cluster_center
    * cluster_extent
    * cluster_policy_stats
虽然你这轮不想先聚焦 reference schema，但接口层面最好预留 reference / coordinate metadata 的扩展位，因为你已经识别到这一点对后续 contract 很重要 。

5. Failure Modes and Engineering Risks
风险 1：Topology 指标过重，选帧变慢
问题
* greedy selection 如果每次都重算完整图指标，复杂度会显著上升；
* 若再引入谱指标，可能在大候选池上变得不可接受。
缓解
* 第一版只做轻量拓扑指标：
    * component count
    * min degree
    * isolated count
    * approximate articulation risk
* 谱指标只做分析，不先放入在线 greedy。
* 采用增量更新，而不是每次全量重算图。

风险 2：auto-stop 过早停止
问题
* 若 adequacy 阈值设置过宽，小场景可能早停在覆盖不足的状态。
缓解
* 设 min_views 下限；
* stop 必须同时满足 coverage adequacy + topology adequacy + gain saturation；
* 第一版在日志里记录 stop reason，并保留强制 fixed_K 回退开关。

风险 3：large-scene gate 误判
问题
* 本来 single-forward 还能做的场景，被误判为 cluster branch；
* 或反之，应该 cluster 的 scene 仍被塞进 single-forward。
缓解
* 使用多统计联合决策，不依赖单一阈值；
* 输出 reason codes，便于调参；
* 先在已有数据集上离线分析 gate 行为，再上线默认启用。

风险 4：ACE cluster 逻辑和 memory branch 的目标不完全一致
问题
* ACE 原始 cluster 是为 ensemble training / relocalization head 设计的；
* 你这里是为 memory construction 设计的，目的不完全一样。
缓解
* 复用其“层次式 camera-center clustering”框架，而不是机械照搬所有细节；
* 增加 cluster-safe 条件，用 single-forward-memory adequacy 来决定是否继续 split。

风险 5：reference 选择仍可能成为隐性瓶颈
问题
* 即便不先解决 reference contract，single branch 的 root/reference 仍可能显著影响 candidate pool 和 topology。
缓解
* 做 reference sensitivity analysis；
* 第一版允许在少量 root candidates 中选一个 probe quality 最好的；
* 后续再系统化解决 reference schema 问题。

风险 6：系统分支过多，工程维护复杂
问题
* 有 single branch、cluster branch、adaptive stop、topology metrics，复杂度上升。
缓解
* 通过统一模块化来控制复杂度：
    * ScenePolicyEstimator
    * SingleForwardSelector
    * ClusterPlanner
    * MemoryPackager
* cluster 内复用 single selector，避免写两套选帧系统。

7. Implementation Roadmap
Phase 0：最小可用原型
目标：在不破坏现有代码主干的前提下，验证方向正确。
做法：
1. 在 run_memory_extraction.py 中增加图统计日志：
    * components
    * min degree
    * isolated count
    * articulation-like risk
2. 先不改主逻辑，只做分析。
3. 用现有 ASB / FPS / native-group 跑一轮，对齐 PoseEval。
产出
* 证明 gap 2 确实存在；
* 找到最相关的 topology 指标。

Phase 1：Single-Forward TA-ASB
目标：完成 small-scene 主路线升级。
做法：
1. 保留 anchor_support_select_views() 主框架。
2. 在 incremental selection 和 _prune_candidate_pool_to_budget() 中加入 topology-aware score。
3. 加入 topology-constrained repair。
4. 保留 fixed-K 模式作为回退开关。
最小可用系统
* 仍然 single-forward
* 仍可设置固定 n_memory
* 但支持 topology-aware selection

Phase 2：Adaptive Stop Controller
目标：把 fixed-K 变成 max_views only。
做法：
1. 新增 adequacy score Q(S)。
2. 新增 min_views / max_views / patience 配置。
3. 记录 stop reason。
4. 做 auto-stop vs fixed-K 比较。
最小可用系统
* small scene 可自适应停止；
* 输出最终选帧数。

Phase 3：Scene Policy Estimator
目标：让系统自动决定 single vs cluster。
做法：
1. 实现 estimate_scene_policy(scene_stats, probe_stats)。
2. 先用 rule-based gate。
3. 在所有 scene 上离线评估误判率和触发分布。
最小可用系统
* 仅输出 policy decision，不真正切 branch；
* 先做离线分析。

Phase 4：ACE-Style Cluster Branch
目标：引入大场景 fallback。
做法：
1. 将 dataset_origin.py::_cluster() 的层次二分 kMeans 逻辑抽成独立 helper 。
2. 实现 split-until-safe。
3. 每个 cluster 内复用 single-forward selector。
4. 输出 clustered memory package。
最小可用系统
* 大场景可以自动 cluster；
* cluster 内仍走统一单批 selector。

Phase 5：系统级整合与稳态版本
目标：形成可长期维护的完整架构。
做法：
1. 抽象出四个清晰模块：
    * ScenePolicyEstimator
    * SingleForwardSelector
    * ClusterPlanner
    * MemoryPackager
2. 整理配置：
    * policy_mode = fixed_single | auto
    * max_views
    * min_views
    * cluster_mode = fixed | auto
3. 建立系统级实验脚本与日志分析。

建议的开发顺序
我建议按这个顺序推进：
1. 先做 topology logging
2. 再做 single-forward TA-ASB
3. 再做 adaptive stop
4. 最后再接 large-scene auto-cluster
原因很简单：small-scene single-forward 是你的主路径，也是你当前系统最重要的基本盘。只有当这条路打稳以后，大场景分支才不会变成“用另一个复杂系统掩盖单分支问题”。
