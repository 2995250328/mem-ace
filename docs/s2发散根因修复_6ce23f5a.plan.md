# ACE-G S2 发散根因分析与修复规划

## Phase 1 结论：根因已确认

### 直接证据（training_full_log.txt, scene3）

S1 迭代 1→27 的首步 `update 1/600` pxErrL1 演变：


| 迭代             | S1 step-0 loss | pxErrL1   | valid%     | 状态                      |
| -------------- | -------------- | --------- | ---------- | ----------------------- |
| iter 1-12      | 19~28          | 43~563px  | 95~99.6%   | 正常                      |
| iter 13-25     | 16~18          | 30~57px   | 99.7~99.8% | 正常（改善）                  |
| **iter 26 S1** | 16.4           | 36px      | 99.8%      | **正常**（iter 25 S2 后仍健康） |
| **iter 27 S1** | **538,363**    | **312px** | **91.6%**  | **灾难性跳变**               |
| iter 28 S1     | 1,266,631      | 32M px    | 62.5%      | 完全崩溃（NaN 权重）            |


关键观察：**iter 27 S1 的第 1 步（更新前）就已经出现 538K loss，说明损坏发生在 iter 26 S2 期间**，而非 S1 训练过程中。

---

### 根本原因：Compressor-Fusion 异步更新导致的渐进式解耦

**S1 更新的参数组**：`self.compressor` + `self.fusion`（同步联合优化）

**S2 更新的参数组**（`_setup_s2_optimizer_and_schedule`，第 1731 行）：

```python
self.optimizer_head = optim.AdamW([
    {'params': self.regressor.heads.parameters(), 'lr': head_lr},     # 1.5e-3
    {'params': self.fusion.parameters(), 'lr': fusion_lr},            # 1.5e-5
    # ← compressor 完全缺席！
])
```

**问题核心**：S2 每轮对 `fusion` 进行 12000 steps × lr=1.5e-5 的更新，而 `compressor` 完全不参与 S2 更新。这导致随着迭代推进：

- `fusion` 在 S2 中不断漂移（total drift ≈ 26轮 × 12000步 × 1.5e-5 ≈ 4.68 单位），以适应当前 regression head  
- `compressor` 输出的 latent tokens 始终基于 S1 上次训练时的 fusion 状态
- 随着 fusion 漂移量积累，compressor 输出与 fusion 期望输入的分布越来越不匹配

**触发点（iter 26 → 27）**：

- iter 26 S2 以异常高的初始 loss（1566）开始，导致 S2 做出超出常规的 fusion 参数更新以恢复
- 这次大幅更新使 fusion 与 compressor 之间的距离发生质变，超出 S1 600 步所能重新同步的范围
- iter 27 S1 第 1 步就显示 pxErrL1=312px（vs 此前 36px），说明在任何 S1 更新发生前，compressor 输出已完全无法被当前 fusion 解读

**级联失效链**：

```
iter 26 S2: 异常高初始loss(1566) → fusion 大幅漂移
    ↓
iter 27 S1 step-0: compressor-fusion 解耦已达质变点 → loss=538K (vs 正常16)
    ↓
iter 27 S1 600步: 无法在有限步数内重新同步 → S1 无收敛
    ↓
iter 27 S2 step-1: 14.5%样本 invalid，loss=883K
    ↓
iter 27 S2 end: valid降至61.9%，pxErr=17M，naninf=92 → 权重NaN
    ↓
iter 28 S1: 检测到NaN → 跳过S2 → 训练终止
```

## Phase 2 评估：已有补丁的定位

上次对话中添加的三项修改均为**症状防护**，不是根因修复：


| 修改                           | 作用层次      | 评价                        |
| ---------------------------- | --------- | ------------------------- |
| `loss_invalid` clamp (1000m) | 损失防护（第3层） | 安全网，不防止解耦                 |
| gradient clipping (1.0 norm) | 梯度防护（第3层） | 安全网，不防止解耦                 |
| `per_iter` soft_clamp        | 恢复能力（第2层） | 有助于 S2 在解耦后恢复，但若解耦幅度过大仍失效 |


**真正缺失的修复**（第1层，预防解耦）：在 S2 中同步更新 compressor。

## Phase 3：精确修复方案

### 主修复：将 compressor 加入 S2 优化器

修改文件：`[ace_depth/trainer_dinov2_lmc.py](ace_depth/trainer_dinov2_lmc.py)`

**位置 1**：`_setup_s2_optimizer_and_schedule`（第 1731~1750 行）

```python
# 修改前
if ace_g_fusion_in_s2:
    self.optimizer_head = optim.AdamW([
        {'params': self.regressor.heads.parameters(), 'lr': head_lr},
        {'params': self.fusion.parameters(), 'lr': fusion_lr},
    ])
    ...
    max_lr=[head_lr, fusion_lr] if ace_g_fusion_in_s2 else head_lr,

# 修改后
if ace_g_fusion_in_s2:
    self.optimizer_head = optim.AdamW([
        {'params': self.regressor.heads.parameters(), 'lr': head_lr},
        {'params': self.fusion.parameters(), 'lr': fusion_lr},
        {'params': self.compressor.parameters(), 'lr': fusion_lr},  # 与 fusion 同步漂移
    ])
    ...
    max_lr=[head_lr, fusion_lr, fusion_lr] if ace_g_fusion_in_s2 else head_lr,
```

**位置 2**：`_training_step_ace_g` 中的梯度裁剪（第 2558~2561 行）

```python
# 修改前
if ace_g_fusion_in_s2:
    params_to_clip += list(self.fusion.parameters())

# 修改后
if ace_g_fusion_in_s2:
    params_to_clip += list(self.fusion.parameters())
    params_to_clip += list(self.compressor.parameters())
```

### 辅助修复：S1 解耦检测告警

在 S1 训练完成后，记录 final loss 与 initial loss 的比值。若 final_loss > initial_loss × 0.9（S1 未收敛），输出 WARNING，便于后续监控。这不影响训练流程，只是预警。

## Phase 4：验证方案

不需要跑 28 个 iter 来验证。可以通过如下轻量方式验证：

1. **S1 step-0 loss 监控**：对比修复前后 iter 26/27 的 S1 update-1 loss。若修复有效，iter 27 S1 step-0 loss 应该维持在 ≤20 的正常范围，而不是 538K
2. **S2 初始损失监控**：修复后 iter 27 S2 step-1 的 loss 应该 ≤100（正常水平），而不是 883K
3. **长训练稳定性**：完整 28-iter 训练中，iter 25-28 的 loss 和 valid% 应与 iter 10-20 保持一致水平
